# Spec: wake on the compositor saying so

Chain (c) of #23, whose intent is the approved problem framing.

## What is on the table, measured

`_await_new_window` (`tools.py:2217-2231`) sleeps 150 ms, queries
`hyprctl -j clients`, repeats. `wait_for` does the same on a 0.35 s / 0.6 s gap.

Measured on this host, five runs, launching a real window:

| | window detected at |
|---|---|
| `socket2` `openwindow` event | **75 ms** |
| today's poll, `sleep(0.15)` | **164 ms** |
| the same poll at `sleep(0.03)` | 94 ms |

Median lag of the current poll behind the event: **91 ms**. One
`hyprctl -j clients` costs 13 ms.

**This is a small win and the spec should say so plainly.** 91 ms against a
model turn of 1.5–7.6 s; roughly 360 ms across a four-pane compose. A tighter
poll alone recovers about 79% of it for one constant. The approved decision is
to build the listener anyway, and the case that justifies it is not the 91 ms:
it is that a `wait_for` can run for 25 s, and polling that at any useful
granularity burns a core for the duration, while a blocked socket read costs
nothing. The 91 ms is a bonus.

## The protocol, as it actually behaves

Captured from the running compositor rather than from documentation:

```
windowtitle>>5d811f0beb30
windowtitlev2>>5d811f0beb30,ev,probe,with,commas
openwindow>>5d811f0beb30,11,foot,ev,probe,with,commas
activewindow>>foot,ev,probe,with,commas
activewindowv2>>5d811f0beb30
closewindow>>5d811f0beb30
```

Three things that will bite anyone who parses this:

1. **Payload fields are comma-separated and titles are not escaped.** That
   window was called `ev,probe,with,commas`, and `openwindow` renders as
   `address,workspace,class,title` with every one of those commas intact.
   Splitting on `,` is wrong and cannot be made right.
2. **Event addresses have no `0x` prefix.** `5d811f0beb30` here against
   `0x5d811f0beb30` from `hyprctl -j clients`. Anything keyed on one will
   silently never match the other.
3. **Event data is truncated at 1024 bytes**, verified in the source this
   Hyprland was built from:
   `EventManager.cpp:128 — std::format("{}>>{}\n", event.event, data.substr(0, 1024))`.

And the one that is not about parsing:

```
EventManager.cpp:169   const size_t MAX_QUEUED_EVENTS = 64;
EventManager.cpp:175   "Socket2 fd {} overflowed event queue, removing"
```

**A client that reads too slowly is disconnected, and is not told why.** There
are no sequence numbers in the stream — the format is `name>>data\n` and
nothing else — so a gap is undetectable from inside. Silence is not evidence of
nothing happening.

## Design

### 1. The listener never parses a payload

This is the decision everything else follows from, and it is the approved
constraint from the intent doing real work: *an event means "recheck", never
"it happened"*, with `hyprctl` authoritative for every consequential read.

If the only question asked of the stream is *did something change*, then only
the text before `>>` is ever read. The payload is discarded unparsed.

That disposes of all three parsing hazards above at once. Unescaped commas in
titles do not matter because titles are never read. The missing `0x` prefix
does not matter because addresses are never read. The 1024-byte truncation does
not matter because only the event name is used, and no event name comes close
to 1024 bytes.

It is also the honest shape: the poll it replaces did not learn anything from
the compositor either — it asked `hyprctl` and looked at the answer. The
listener replaces the *sleep*, not the query.

### 2. A thread that only drains the socket

`src/omarchy_voice/hypr_events.py`: connect to
`$XDG_RUNTIME_DIR/hypr/$HYPRLAND_INSTANCE_SIGNATURE/.socket2.sock`, read, split
on `\n`, and for each line take the name before `>>` and set a
`threading.Event` if it is one we care about.

The thread does **nothing else**. Not matching, not querying, not calling back
into `Executor`. That is the direct mitigation for `MAX_QUEUED_EVENTS`: 64
queued events is generous for a reader that only reads, and fatal for one that
stops to do a `hyprctl` query per event during a workspace switch that emits
dozens. Work happens on the waiting thread, after it wakes.

Partial reads are buffered and only complete lines are consumed — `recv` splits
wherever it likes, and a name split across two reads would otherwise be lost.

Events worth waking for: `openwindow`, `closewindow`, `movewindowv2`,
`windowtitle`, `windowtitlev2`, `activewindow`, `activewindowv2`, `workspace`,
`focusedmon`, `fullscreen`, `changefloatingmode`. Over-waking is free — the
waiter re-queries and goes back to sleep — so the list errs wide. Under-waking
is a missed wake-up, and the poll below covers that anyway.

### 3. The poll does not go away

The waiter sleeps on `event.wait(gap)` rather than `time.sleep(gap)`, so it
wakes on whichever comes first. `gap` backs off, per the approved answer:
**30 ms for the first second, then 150 ms.**

Both halves earn their place:

- The fast first second is what happens when the listener is unavailable — no
  socket, a compositor restart, a disconnect we have not noticed yet. It
  recovers 94 ms-class detection on its own, so the feature degrades to
  *slightly worse than the listener* rather than to nothing.
- The backoff is why a wait that never succeeds does not hold a core. The
  failure case costs about what it costs today.

With the listener working, the event fires at ~75 ms and the 30 ms tick never
gets a second iteration. With it broken, nothing above this layer notices.

### 4. Failure is expected, not exceptional

- **No socket, or connect fails** → no listener, poll only. Not an error; this
  is also what happens under `nix flake check`, where there is no compositor.
- **EOF or a read error** → the compositor went away or disconnected us for
  overflowing. Mark unavailable and reconnect with backoff. Do not assume the
  state we last saw still holds.
- **`hyprctl reload`** → nothing special. Because no state is cached, there is
  nothing to invalidate. This is the second place the no-parsing decision pays.
- **Connect before the baseline.** A waiter subscribes, *then* takes its first
  `hyprctl` reading. The other order loses anything that happens in between.
  And because an event only means "recheck", a waiter that is woken
  spuriously — or that finds the condition already true on its first
  check — behaves correctly by construction.

### 5. Never `Executor._lock`

The listener thread must not need the executor lock, and a tool holding that
lock must be able to wait on an event. The listener touching only a
`threading.Event` is what guarantees this; it is called out because it is the
deadlock this design could have had.

### 6. One listener per process

Created lazily on the first wait and shared. The daemon is long-lived and
`omarchy-voice mcp` is not — nine of those were running on this host at once
while writing this — so a listener per wait would be nine sockets and nine
threads against a compositor that disconnects clients it thinks are slow.

## Alternatives rejected

- **An in-memory clients/workspaces/monitors table fed from the stream.** The
  intent already rules it out, and everything above is the reason: it would
  require parsing payloads, which reintroduces the comma escaping, the `0x`
  prefix, the 1024-byte truncation and the undetectable gaps — to save 9.5 ms
  per query against a 1.5–7.6 s turn.
- **A tighter poll and no listener.** Measured at 94 ms, ~79% of the win, ~10
  lines, no new failure modes. Put to the approver with those numbers and
  declined in favour of the listener, for the 25 s-wait CPU case. Recorded
  because it remains the fallback if the listener proves troublesome, and
  because step 3 builds it anyway.
- **Parsing `openwindow` to learn the new window's address.** Tempting — it is
  right there in the payload — and it is the decision that would drag in every
  hazard in section "The protocol". The address is 13 ms away from `hyprctl`.
- **`hyprctl --instance` / a second socket for queries.** Different socket,
  different problem; `.socket.sock` is 3.5 ms against `hyprctl`'s 13 ms and
  that is #23's rejected micro-optimisation, not this.

## Risks

- **The win is small and the code is not.** Stated up front rather than
  discovered later. If the #26 trace shows waits are not a meaningful share of
  task time, the honest response is to say so and keep step 3 only.
- **A disconnect we fail to notice degrades silently.** The poll means it stays
  correct, just slower — which is the failure mode to want, but it also means
  nobody finds out. The listener should record its state where `doctor` can
  report it.
- **Over-waking costs a `hyprctl` query per event.** During a workspace switch
  that is a burst. Bounded by the waiter's own `gap`, since a wake that arrives
  inside the same tick collapses into one re-check.
- **Tests must not need a compositor.** The suite runs in the nix sandbox. The
  listener has to be injectable, and the poll-only path is the default there.
- **This is the third thing in `tools.py` that waits.** `_await_new_window`,
  `wait_for` and now `_await_paint` from #26 all have their own loop. This
  spec does not unify them, and should say so: `_await_paint` waits on pixels,
  not on the compositor, and folding it in would put an OCR read behind an
  event that will never fire for it.

## Verification

1. **The listener beats the poll, measured the same way as the numbers above.**
   A window launch is detected at ~75 ms rather than ~164 ms. This is the
   claim; it is measured on the live desktop, not asserted.
2. **No payload is ever parsed.** A window whose title contains commas — the
   `ev,probe,with,commas` case — wakes the waiter and resolves correctly, and
   the listener's own state contains nothing derived from the payload.
3. **A missing socket degrades to the poll**, with no error surfaced to the
   model. Asserted with `XDG_RUNTIME_DIR` pointed somewhere empty, which is
   also how this passes in the sandbox.
4. **EOF reconnects**, and a waiter running across the disconnect still
   completes — on the poll, at poll speed.
5. **The gap backs off.** A wait that never succeeds issues roughly today's
   number of queries, not thirty times as many. Asserted on a fake clock.
6. **The condition already being true returns immediately**, without waiting
   for an event that will never come, because the waiter checks before it
   sleeps.
7. **No deadlock.** A test holds `Executor._lock` while a waiter waits and the
   listener delivers, and it completes.
8. **Existing waits are unchanged in behaviour.** Every current
   `_await_new_window` and `wait_for` test passes untouched.
9. **Suite and gate.** `nix develop -c python3 -m unittest discover -s tests`
   green, `nix flake check` passes (no compositor there — see 3),
   `omarchy-voice verify-gate` exits 0.
