# Spec: name a window and the tool finds it

Chain (b) of #23, whose intent is the approved problem framing.

## What is actually wrong

The issue was filed against `_window_matches` (`tools.py:451-461`), a lowercase
substring over four concatenated fields. Reading the code first, as the intent
requires, the matcher turns out to be the smaller half.

`_window_matches` has **two** callers: `_await_new_window` (`tools.py:2226`) and
`wait_for(window|window_gone)` (`tools.py:3085`). The tools that *look at* a
window do not use it. Measured on the live system:

```
_target_geometry('class:google-chrome')
  -> no window with address 'class:google-chrome' — call hypr_query(clients) for current addresses
_target_geometry('chrome')
  -> no window with address 'chrome' — ...
```

`read_screen`, `click_text`, `scroll` and `wait_for` accept only `"screen"`,
`"activewindow"` or a literal `address:0x…`. `send_shortcut` is the exception:
it hands the selector to Hyprland, which resolves `class:chromium` itself.

So "read my email window" costs:

1. `hypr_query(clients)` — 1942 characters, ~485 tokens, back to the model —
   **one model turn**
2. read the JSON, pick the address, `read_screen(target="address:0x…")` —
   **a second model turn**

Two model turns at 1.5–7.6 s each, for a lookup the code does in 13 ms. The
refusal above even instructs the model to spend the first one.

That is the "we spend a lot of time finding windows" complaint, located. The
trace from #26 supports the shape of it: on a task whose only tool work was a
query and a read, `lock=0.00s` and the time was model turns and OCR. Nothing
here is won by making the lookup faster; it is won by not needing the turn.

## Design

### 1. One resolver

There are already two near-identical ones, which is the usual sign:

| | returns | used by |
|---|---|---|
| `_target_geometry` (`tools.py`, added in #26) | a grim geometry string | `read_screen`, `click_text`, `wait_for(text)` |
| `_window_geometry` (`tools.py:2951-2966`) | the client dict | `scroll` |

Both do the same address lookup and both carry the same "call hypr_query"
error. Collapse to `_resolve_window(target) -> tuple[dict | None, str]`
returning the client or a reason, handling in order:

- `""`, `activewindow`, `active`, `focused` → `focusHistoryID == 0`, as today.
- `address:0x…` or a bare `0x…` → exact address, as today.
- `class:foo`, `title:foo` → that field only. Hyprland's own selector syntax,
  which `send_shortcut` already accepts; supporting it here removes a
  difference between tools that has no reason to exist.
- anything else → **ranked by name** (below).

`_target_geometry` becomes `_resolve_window` plus the `"screen"` case, the
visible-workspace guard and the geometry string. `_window_geometry` becomes a
thin call. `scroll`, `read_screen`, `click_text` and `wait_for` all gain
by-name targeting from the one change.

### 2. Ranking

`_rank_windows(clients, name) -> list[tuple[float, dict]]`, best first. Scored
on, highest wins:

1. exact `class` match, case-insensitive
2. `class` starts with the name
3. name appears in `class` or `initialClass`
4. name appears in `title` or `initialTitle`

Two adjustments, each for a reason already visible in this codebase:

- **`initialTitle` counts as much as `title`.** The existing docstring records
  why: a web app retitles itself the moment it loads, so `initialTitle` is
  "www.bbc.com_/news" while `title` is a headline a second later.
- **`focusHistoryID` ascending orders equal scores.** `_await_new_window`
  already sorts that way (`tools.py:2230`).

  **Corrected during implementation:** this originally said ties *break*
  toward the focused window, which contradicts "ambiguity is a question" two
  sections below — they collide exactly when two equal-scoring windows exist
  and one is focused. The question wins. Focus decides which candidate is
  named first in the refusal, not which window is chosen; `activewindow`
  already exists for anyone who means "the one I am looking at".

No fuzzy-distance library. Nothing is added to `nix/package.nix:63-83` for a
scoring function that is four `in` tests, and an edit-distance match on window
titles invents confidence nobody asked for.

### 3. Ambiguity is a question, not a guess

If the best two candidates score equally, `_resolve_window` returns no window
and an error naming them:

```
"chrome" matches 3 windows: google-chrome "Issues · olafkfreund/Factory"
(workspace 4), google-chrome "Gmail" (workspace 2), google-chrome "Calendar"
(workspace 2). Say which, or pass one of their addresses.
```

This is the hard constraint from the review and it is not negotiable for
speed. The policy gate matches a one-line description (`tools.py:63-77`), so a
silently-chosen wrong target produces a *correct-looking* description of the
wrong action. Costing a turn to disambiguate is the right trade; the turn this
chain removes is the one spent on `hypr_query` when the name was unambiguous,
which is the common case.

A tie is equal scores, not close scores. "Chrome" against one Chrome window and
one terminal titled "chrome-flags.conf" is not a tie — class beats title — and
turning that into a question would put the turn straight back.

### 4. `_window_matches` keeps its job, on the new scorer

Its two callers ask a different question — "has anything matching this appeared
or gone?" — where ranking is meaningless but better matching still helps. It
becomes `_rank_windows(...) != []` for that one client, so there is one
definition of what a name matches rather than two that will drift.

### 5. What the model is told

`TOOL_SCHEMAS` descriptions for the four tools change from `"address:0x..."` to
name-or-address, and the `hypr_query(clients)` advice comes out of the refusals
in `_resolve_window` — it is the round trip this chain exists to remove, and
leaving the instruction in would keep the model paying it.

## Alternatives rejected

- **Only fix `_window_matches`.** What the issue asked for. It improves two
  callers and leaves the two-turn cost untouched, which is the whole finding
  above.
- **Resolve names inside Hyprland** by passing `class:foo` through to the
  dispatcher, as `send_shortcut` does. Works for dispatching; useless here,
  because `read_screen` and `scroll` need the window's *rectangle*, and
  Hyprland's selector resolves inside a dispatch rather than handing back
  geometry. It also has no ambiguity story: Hyprland picks one.
- **A fuzzy-matching dependency** (RapidFuzz was suggested in review). A new
  runtime input for four `in` tests, and edit distance over titles would score
  "Gmail" against "Calendar" as meaningfully different by an amount nobody can
  reason about.
- **Pick the best match and say which one you picked.** Cheaper by a turn, and
  it puts a wrong target behind a right-looking description. Rejected on the
  review's constraint.
- **Cache the client list.** #28's territory, and the trace says the query is
  13 ms. Nothing to win.

## Risks

- **Ranking that is confidently wrong is worse than a substring miss.** A miss
  costs a turn; a wrong pick acts on the wrong window. Mitigated by the
  class-over-title ordering and by ties being questions — and the wrong-target
  rate is already a metric the #26 trace reports, so this is measurable rather
  than argued.
- **The ambiguity message costs tokens.** It lists candidates with class, title
  and workspace. Capped at a handful, and it replaces a 485-token
  `hypr_query` dump, so it is cheaper than what it removes.
- **`_window_matches` changing definition changes `wait_for`.** Its two callers
  become more permissive: a name that matched nothing may now match. For
  `wait_for(window_gone)` more permissive means it may report "still open"
  where it used to say "gone" — which is the safer direction, but it is a
  behaviour change and needs its own test.
- **Collapsing two resolvers touches four tools at once.** Mitigated by the
  existing tests for each, which already cover the address and activewindow
  branches; the refactor must pass them untouched.

## Verification

1. **By name, in one call.** `read_screen(target="chrome")` resolves to the
   Chrome window's geometry with one `clients` query and no error — the two
   turns become one.
2. **Class beats title.** A window of class `google-chrome` and a terminal
   titled `chrome-flags.conf`: `"chrome"` resolves to the browser, and it is
   not reported as ambiguous.
3. **A real tie is refused, and names the candidates.** Two `google-chrome`
   windows, `"chrome"` → no window, an error containing both titles and both
   workspaces, and **no capture attempted**.
4. **Ties break to the focused window.** Two windows of the same class, one
   with `focusHistoryID: 0` → that one, no ambiguity error.
5. **`initialTitle` still counts**, using the web-app case the existing
   docstring describes.
6. **Explicit selectors work**: `class:foo` and `title:foo` match only that
   field, so `title:chrome` does not find a window of class chrome.
7. **Nothing regressed on the old forms.** Every existing test for
   `read_screen`, `click_text`, `scroll` and `wait_for` passes untouched —
   `activewindow`, `address:0x…` and a bare `0x…` behave exactly as before.
8. **`wait_for(window_gone)` gets its own test** for the widened matcher.
9. **The refusals no longer send the model to `hypr_query`.** Asserted by
   searching the error strings, so the round trip cannot creep back in as
   advice.
10. **Suite and gate.** `nix develop -c python3 -m unittest discover -s tests`
    green (640 at the time of writing), `nix flake check` passes,
    `omarchy-voice verify-gate` exits 0, and `read_screen(target="chrome")`
    works against the live desktop.
