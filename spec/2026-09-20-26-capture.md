# Spec: stop spending a second on PNG, and stop sleeping 2s on faith

Chain (a) of #23, whose intent is the approved problem framing for this and for
#27 and #28.

## Measurements this design rests on

Re-measured while writing this, on the live machine, 2560x1440:

| | |
|---|---|
| `grim -g 2560x1440 -` (PNG), mean of 5 | **0.940 s** |
| `grim -t ppm -g 2560x1440 -`, mean of 5 | **0.032 s** |
| tesseract, full monitor, sparse screen | 1.1–1.2 s |
| tesseract, full monitor, ~1500 chars of text | 1.9–2.4 s |
| tesseract, full monitor, text-dense | up to 5.3 s |
| tesseract, 800x600 region | 0.84 s |

**A correction to the intent.** It quotes `grim | tesseract` at 3.97 s as though
that were the number. It is not: OCR time is content-dependent and the honest
range is roughly **1–5 s for a full monitor**, most often 1–2.5 s. The 3.97 s
was one text-dense screen. I also checked whether this host's 128 cores were
causing the variance — `OMP_THREAD_LIMIT` from 1 to 128 is flat at 1.1–1.3 s on
a fixed image, so it is the content, not thread contention.

The conclusion is unchanged, and in one respect strengthened: the reason to
scope OCR to a window is not only fewer pixels but *less text*, and text is
what tesseract charges for.

The `grim` number is content-independent — it is PNG compression of a
fixed-size framebuffer — and it is the one unambiguous win here.

## Design

### 1. `grim -t ppm` at both capture sites

`_ocr_region` (`tools.py:1828`) and `_ocr_words` (`tools.py:1922`) both run
`grim -g <geom> -` and pipe the bytes straight into tesseract. Neither keeps
the image. The PNG encode is ~0.9 s of work on output that is decoded and
discarded microseconds later.

Add `-t ppm`. Nothing else changes: tesseract reads PNM natively from stdin, as
`stdin` already implies. The pipe carries more bytes (11 MB versus 2.5 MB for
this framebuffer), which is memory traffic between two local processes and does
not appear in the measurements above — both were taken through the pipe.

This is the whole of step 1, and it lands first per the approved sequencing.

### 2. The trace

`tools/bench_local.py` gains per-phase timestamps for whole tasks, not
components: utterance end, each model turn boundary, `Executor._lock`
acquisition, each subprocess with its argv[0], capture, OCR, and verified
completion.

Reported as:

- p50 and p95 **task completion**, not stage means.
- **Dependent model continuations** — the number of times the model had to be
  called again *because* it was waiting on a tool result. Not tool calls: a
  model can issue several in one response, and those cost one turn, not three.
  This is the number the deferred composite-tool work in #23 would move.
- **Wrong-target rate** — how often the action landed on something other than
  what was asked for. A change that halves latency and doubles this is a loss.

Also emitted to `session.log` behind a flag, **off by default**, named under
`[hands]` alongside the existing `allow_notifications` and `desktop_control`
(`config.py`). Per the approved answer: durations and phase names only. No
window titles, no OCR text, no tool arguments. A timing flag that quietly
records what you were reading would be a worse version of the notification log
that #19 just made opt-in, and the whole value here is in the durations.

The flag exists because a bench run by hand only measures the tasks someone
thought to script, and the slow turns that matter happen in real use.

### 3. Scope OCR to the target rect

`_read_screen_text` already resolves a target to client geometry, and
`_read_web_window` (`tools.py:2710`) uses the window's `at`/`size`. Two callers
still capture a whole monitor:

- **`click_text`** (`tools.py:2016-2022`) takes the focused monitor
  unconditionally. It gains an optional `target` argument, defaulting to the
  current behaviour. **Deliberately not defaulting to the active window**: the
  thing being clicked is often not in it — a bar widget, a dialog that has not
  taken focus, a second window being pointed at. Silently narrowing where it
  looks would turn "did not find it" into the common case, and the model's
  recovery from that is another turn, which is the cost this chain exists to
  remove.
- **`wait_for(what="text")`** re-runs the full pipeline every 0.6 s for up to
  25 s. It gains the same optional target. This is where scoping pays most: the
  saving is multiplied by the number of iterations.

`--dpi 300` stays for now. It overrides the input's resolution metadata; it does
not rescale the bitmap, so removing it is an OCR-accuracy experiment, not an
optimisation. Measured: dropping it took a full-screen read from 1.12 s to
0.96 s but also from 1769 to 1013 characters recovered — it is doing real work.
Out of scope here; worth its own look if accuracy ever needs tuning.

### 4. Replace `WEB_RENDER_SETTLE`

`_read_web_window` (`tools.py:2701-2708`) opens with `time.sleep(settle)`,
`settle = 2.0`, unconditionally, plus a second 2.0 s on the retry path.

Replace with a bounded poll: capture at a short interval, stop when the read
stabilises or yields enough text, give up at the current 2.0 s. Worst case is
what happens today; the common case is a page that painted in 300 ms.

The trap is already documented in that function at `tools.py:2704-2706` — a
window is mapped well before it has drawn anything, so neither `openwindow` nor
the window's existence is the predicate. The predicate has to be about pixels
or text, which is why this sits in the capture chain and not in #28.

Re-read the window geometry after the wait. The current code computes
`geometry` once and reuses it; a window that was still being placed when the
read started gets OCR'd at its old rect.

## Alternatives rejected

- **Keep PNG but drop compression (`grim -l 0`).** Measured at 0.056 s, close
  to PPM's 0.032 s. PPM is simpler — no compression level to explain — and the
  consumer is a pipe, so the container format buys nothing.
- **Tune tesseract's page-segmentation mode.** `--psm 6` measured faster
  (0.91 s vs 1.12 s) but recovered 592 characters against 1769. It assumes a
  uniform block, and a desktop is not one. `--psm 11` was both slower and worse.
  `--oem 0` (legacy engine) was 2.6 s. The current flags are the right ones.
- **Cap tesseract's threads.** Investigated because this host has 128 cores and
  the pipe timings varied 1.3–5.3 s. `OMP_THREAD_LIMIT` is flat from 1 to 128;
  the variance was screen content. No change.
- **Default `click_text` to the active window.** See above — it would trade
  seconds of OCR for turns of recovery.
- **Drop `--dpi 300`.** Measured to cost 40% of the recovered text.

## Risks

- **PPM through the pipe is 4x the bytes.** Both measurements above were taken
  through the pipe, so it is already accounted for. It would matter on a
  memory-constrained host; this is not one, and the alternative is 0.9 s of CPU.
- **A scoped `click_text` that the model does not scope changes nothing.** The
  default is the current behaviour, so this step's benefit depends on the
  manifest teaching the target argument. If the trace shows it unused, the
  honest response is to say so, not to force a narrower default.
- **Replacing the 2 s sleep can make a slow page worse, not better.** A poll
  that stops early on a partially-painted page returns less than the sleep
  would have. The stability predicate needs a floor, and the retry path has to
  stay.
- **The `session.log` flag is a privacy surface.** Mitigated by logging only
  durations and phase names, and by defaulting off. Worth a test asserting that
  no tool argument reaches the log through it.
- **The trace measures this machine.** p95 on a 128-core desktop is not p95 on
  a laptop. The numbers are for comparing before and after on one host, not for
  publishing as the project's performance.

## Verification

1. **`grim -t ppm` is used.** Both call sites assert on the argv through the
   existing seam — `tests/test_reach.py:44-64` patches `Executor._shell`, and
   these two use `subprocess.run` directly, so the test patches that.
2. **OCR output is unchanged.** Same saved frame, PNG and PPM, identical
   tesseract text. A fixture image, not a live capture, so it is reproducible
   in the nix sandbox.
3. **The trace reports the right thing.** A unit test over a synthetic sequence
   of phase events asserts that two tool calls in one model response count as
   **one** dependent continuation, not two. That distinction is the entire
   point of the metric and is easy to get wrong.
4. **The log flag is off by default and leaks nothing.** With the flag on, a
   task that reads the screen produces log lines containing durations and phase
   names and **not** the OCR text, the window title, or any tool argument.
5. **Nothing sleeps unconditionally.** `_read_web_window` against a window that
   paints immediately completes in well under 2 s; against one that never
   paints it still gives up at the current bound and still retries once.
6. **Geometry is re-read after the wait**, asserted by moving the window
   between the wait and the read in a stubbed client list.
7. **Suite and gate.** `nix develop -c python3 -m unittest discover -s tests`
   green (620 at the time of writing). `nix flake check` passes.
   `omarchy-voice verify-gate` exits 0.
8. **The before/after that justifies the chain.** The step-2 trace, same task
   list, run before step 3 and after step 4, reported as p50/p95 task
   completion, dependent continuations and wrong-target rate. Step 1 lands
   before the trace exists by the approved sequencing, so its evidence is the
   `grim` measurement above rather than a task trace — that is the one place
   this chain accepts a component benchmark, and it does so because the change
   is two flags and the number is content-independent.
