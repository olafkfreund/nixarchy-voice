# Plan: A published page, a real demo, and a story a new user can follow

## Approved decisions (from the spec, complete)

1. **Recording host: razer** (`eDP-1`, 1920x1080). Never p620. Oma's voice
   there is Piper "Jenny"; there is no ElevenLabs key and desktop control is
   off.
2. **The requests are typed turns, shown as captions.** Every feature shown
   runs for real; nothing is mocked or staged. An optional `--live` clip uses
   the microphone if the user is at razer.
3. **Capture:**
   - `gpu-screen-recorder -w eDP-1 -f 30 -a default_output -c mp4` on razer;
   - fallback, if the pre-flight test shows frozen frames: `grim -t jpeg`
     frames plus `pw-record` of the sink monitor, joined with ffmpeg.
4. **`demo/shots.toml`**, one shot list with a beat each for:
   1. toggle on;
   2. ask to make `demo-focus`, and hear the readback;
   3. confirm;
   4. Menu ▸ Run, showing `git status` in the `Oma` session;
   5. run the demo tests and get `exit 1`;
   6. uptime;
   7. the `demo-hello` routine's notification;
   8. the end card.

   Each beat has `action`, `hold`, `expect` and `caption`. The same file
   drives the take, `verify` and the captions.
5. **Scripts in `demo/`:**
   - `rz`: runs a command on razer inside its Hyprland session environment;
   - `prep`: refuses rather than tidies;
   - `record`, `verify`, `edit`;
   - `restore`: idempotent.
6. **`prep` sets up the take:**
   - it refuses if any window or notification is open;
   - it saves the theme (Osaka Jade), the wallpaper and DND to a state file;
   - it switches to Tokyo Night and turns DND on;
   - it uses an empty workspace;
   - it creates the demo repo `/tmp/oma-demo`, a `git init` whose `make test`
     exits 1;
   - herdr stays out of shot.

   **`restore`** puts all of that back, deletes the `demo-*` actions and
   routine units and `/tmp/oma-demo`, then re-reads the live state to confirm.
7. **`verify` checks the raw master:**
   - OCR at each beat's observed time must find its `expect`;
   - it refuses a file that already has captions;
   - the audio must not be silent.
8. **`edit` makes, from the one master:**
   - `docs/media/oma-demo.mp4`: 1280x720, H.264 plus AAC, captions burned in,
     loudness-normalised, `+faststart`, under 8 MB (otherwise a release asset);
   - the poster `oma-demo.jpg`;
   - stills: `actions-menu.png`, `readback.png`, `routine-notification.png`,
     `bar-widget.png`;
   - the nixarchy GIF: a 1728x1080 centred crop, 4 fps, 900 px, 96 colours,
     under 1 MB.

   `docs/media` stays under 12 MB in total.
9. **The page:** `docs/omarchy-voice.html` is replaced by `docs/index.html`
   (removed, not kept alongside).
   - It keeps the design: tokens, light and dark themes, Chivo and IBM Plex.
   - New content: a hero video, what Oma is, what it does, setting it up, what
     it costs, the safety model, and the screenshots.
   - No 0.3 claims and no hard-coded tool or test counts.
   *Changed by the user (2026-09-27):* the page takes **nixarchy's look and
   feel**, not the old page's design. It uses nixarchy's `docs/assets/style.css`
   (copied, with only the wordmark sizing scaled from 92 to 50 columns), JetBrains
   Mono, and a figlet `delta_corps_priest_1` "VOICE" wordmark in its green, and
   follows nixarchy's front-page pattern (heading, one sentence, two CTA
   buttons, reading column, wide media). Plain HTML with no Jekyll. Built
   *before* take 2, so it has no media yet: the video, poster and stills are
   added when the take exists. Nothing is mocked in the meantime.
10. **`.github/workflows/pages.yml`**:
    - on push to `main` touching `docs/**`, plus `workflow_dispatch`;
    - configure-pages → upload-pages-artifact (`docs`) → deploy-pages;
    - `pages: write`, `id-token: write`.

    It's flagged for review in the PR.
11. **README:** a new `## Getting started` after the opening paragraphs,
    ~60 lines. Its steps:
    1. install (nixarchy's *Set up voice* or
       `programs.nixarchy.voice.enable`; otherwise the HM module);
    2. sign in to Claude Code;
    3. `SUPER + SHIFT + V`, or the bar widget;
    4. three first sentences;
    5. a first action;
    6. a first routine;
    7. when it doesn't work.

    The page mirrors these steps and links to the README section.
12. **Corrections:**
    - the README's terminal text (571-581, 602): paste, the `Oma` session,
      a named target must be visible, non-zero is a failure;
    - uptime from `/proc` (599, 859);
    - HANDOFF.md 173, 176-181 and 410;
    - README Layout `planner.py`, checked against the code first.
13. **nixarchy#1022 is not written from here.** This repo hands over:
    - the GIF;
    - the Actions still;
    - the page URL;
    - the measured closure size voice adds (`nix path-info -S`, voice on
      against voice off).

## Steps

Each step is its own commit on `docs/163-page-demo-user-story`. Any step that
touches razer's desktop is announced on the agent bus first, and released
after.

1. **`demo/rz` and the pre-flight test.**
   - Record 5 s on razer with the `gpu-screen-recorder` command (decision 3).
   - Sample 5 frames with ffmpeg; they must not all be identical (compare
     hashes).
   - Check that `ffmpeg -af volumedetect` on the audio, taken while
     `omarchy-voice listen say "hello"` speaks, shows a `max_volume` above
     −40 dB.
   - Use the fallback if either fails.

   → Verify: the chosen method is recorded here, with the numbers.
   *Recorded (2026-09-27):* **gpu-screen-recorder works on razer; no
   fallback.** A 9 s take with a notification appearing: 14 frames at 2 fps, 8
   distinct, so the picture is live (unlike `wl-screenrec` there). The stream is
   1920x1080 H.264 at 30 fps plus Opus audio. Oma's Piper reply: mean −23.3 dB,
   peak 0.0 dB but flat factor 0 and peak count 2, so she is not clipped: it is
   Piper's normalised peak, and `edit`'s loudnorm (TP −1.5) handles it. The
   monitor capture does not follow the sink volume (24% and 45% gave the same
   level), so `prep` need not touch the volume.
2. **`demo/shots.toml`, `demo/prep`, `demo/restore`.**
   *Deviations (step 2):* one driver, `demo/demo.py`, with subcommands prep,
   record, verify, edit and restore, instead of six scripts: the shot loop
   needs TOML and timing either way. **No Do Not Disturb:** this Omarchy has
   no command for it, and DND would also hide beat 7's own notification.
   `prep`'s refusal plus a by-eye review of every beat frame cover leakage
   instead. *Recorded:* prep refused with a foot window open ("close them
   first: foot (foot)"); with none, it saved {Osaka Jade, Glowing City, ws 3,
   idle} and set up Tokyo Night, ws 7, /tmp/oma-demo and demo-hello; restore
   gave back Osaka Jade, Glowing City (theme set restores its background),
   ws 3, 0 windows, no demo files, no actions, idle, 0 failed units.
   - Run prep, then restore, with no take in between.

   → Verify:
   - prep refuses while a window is open (tested by opening one);
   - after restore: the theme is Osaka Jade again, `/tmp/oma-demo` is gone,
     no `demo-*` actions or units remain, and there are 0 failed units.
3. **`demo/record` and `demo/verify`: a full take.**

   → Verify:
   - `verify` passes, with every `expect` found and the audio not silent;
   - I look at a still from each beat: nothing private is visible, and the
     frames are attached to the PR for your eye.

   A failed beat is investigated and fixed, and never faked. A real bug gets
   *Take 1 (2026-09-27), discarded, findings:*
   1. **Never open the mic in a take.** Beat 1 (`listen start`) had Oma hear
      people talking near razer and answer them on the track; the take was
      deleted. Beat 1 is removed; typed turns need no listening.
   2. **A new interactive shell on razer shows a greeting with the user's
      calendar, tasks and unread mail.** Any terminal in shot would publish
      it. `prep` will pre-create Oma's `Oma` tmux session as a clean
      `bash --norc` in /tmp/oma-demo, which `run_in_terminal` attaches to.
   3. **The Omarchy menu on razer has its own dictation:** a waveform and
      "Finishing transcript…", with Return meaning Finish. It transcribed the
      room ("Thank you") and ate the Run keypress. Its trigger is not found
      yet (razer's shell is a different build from p620's). Needs the user.
   4. razer has `allow_shell = false`, so "run the tests" is held. The beat
      must confirm it, which shows the gate working.
   5. The readback is spoken only, so that beat is checked by ear
      (`expect_audio`). OCR needed a 2x, grey, inverted frame, and
      volumedetect needs info-level output. Both are fixed in `verify`.
   6. `restore` missed the `Oma` tmux session: razer's socket is under
      XDG_RUNTIME_DIR. Fixed, and `restore` now checks for the session.
   *Take 2, discarded:*
   1. The menu's "dictation" belongs to nixarchy.menu itself. `toggle()` on
      an open palette with `secondTap = "voice"` starts Voxtype dictation
      (NixarchyMenu.qml:57). Menus are now closed with Escape, and only when
      open; never with a second toggle.
   2. A command held in take 1 was still pending in razer's daemon. Take 2's
      save was refused (one hold at a time) and its confirm released the old
      command. The session had also carried 13 turns (~491k tokens) across
      takes. `prep` now restarts Oma for a fresh daemon per take, and
      `restore` cancels any hold.
   3. Another agent took razer during the take, despite the claim. It was
      asked on the bus to respect claims.

   The clean Oma tmux session worked: no private greeting on screen.

   *Takes 3-5, discarded, one beat each:*
   - nixarchy.menu ranks rows by use (`usage.json`, keys
     md5("omarchy/<row id>")), so a row's position changes after every take:
     Down×3 hit Approve in take 3 and Edit in take 5.
   - Typing does not filter a submenu, because the search is global (take 4).
   - Purging the demo keys and restarting the shell did not hold either. The
     old shell writes its in-memory copy back as it exits (take 5).

   **Fix:** `menu_pick` OCRs the row-label column (`626,335 260x380`, below
   the header and above the footer, whose "Run ↵" hint once read as a row)
   and presses Down as many times as the row needs. Tested on both demo
   submenus before the take: it reads the order exactly.

   *Take 6, kept (2026-09-27):* `verify` passed every beat. It heard the
   readback (−19.3 dB) and found `demo-focus` in the menu at 36 s,
   "No commits yet" at 57 s, "Error 1" at 78 s, the uptime answer (−19.4 dB)
   and the "Oma: demo-hello" notification at 149 s. `menu_pick` read the
   rows [Run, Edit, Approve, Delete] and [Routine, Edit, Approve, Run,
   Delete]. The by-eye review of 12 frames found nothing private: the
   Tokyo Night desktop, the menu, the public GitHub page, and Oma's clean
   terminal. razer was restored and re-checked.

   *Step 4, recorded:*
   - `oma-demo.mp4`: 1280x720, H.264 plus AAC, 3:10, 3.3 MB.
   - Stills: 0.5-0.6 MB each.
   - `docs/media` total: 5.1 MB.
   - The nixarchy GIF was 1.33 MB from confirm to end, over 1 MB. It now
     spans the menu Run only (beat start +1.6 s to seen +1 s): 900x563, 60
     frames, 0.94 MB. `edit` refuses a GIF of 1 MB or more.
   - Captions are wrapped at 56 characters, one centred drawtext per line;
     the first cut ran off both edges of the frame.
   its own issue.
