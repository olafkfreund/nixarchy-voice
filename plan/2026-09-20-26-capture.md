# Plan: capture — ppm, a trace, scoped OCR, no fixed sleep

## The approved decisions, in full

Implementable without opening the intent or the spec.

**The problem.** Reading the screen is the expensive thing the assistant does,
and about a second of every read is PNG compression on an image that is piped
straight into tesseract and discarded. Above that, a fixed `time.sleep(2.0)`
runs before every web page read whether the page painted in 300 ms or not.
Finding a window, by contrast, costs 13 ms — so this chain is where the seconds
are.

Measured on this host, 2560x1440:

| | |
|---|---|
| `grim -g 2560x1440 -` (PNG), mean of 5 | **0.940 s** |
| `grim -t ppm -g 2560x1440 -`, mean of 5 | **0.032 s** |
| tesseract, full monitor, sparse screen | 1.1–1.2 s |
| tesseract, full monitor, ~1500 chars | 1.9–2.4 s |
| tesseract, full monitor, text-dense | up to 5.3 s |
| tesseract, 800x600 region | 0.84 s |

OCR time is content-dependent — the honest range is 1–5 s for a full monitor,
most often 1–2.5 s. `OMP_THREAD_LIMIT` is flat from 1 to 128 on a fixed image,
so the variance is screen content, not this host's core count. The `grim`
number is content-independent and is the one unambiguous win.

Decisions carried over:

1. `grim -t ppm` at both capture sites. Lands first, before the trace, by the
   approved sequencing; its evidence is the measurement above rather than a
   task trace, and that is the only component-benchmark exception this chain
   allows.
2. The trace reports p50/p95 **task completion**, **dependent model
   continuations** (not tool calls), and **wrong-target rate**.
3. Trace output also goes to `session.log` behind a flag that is **off by
   default**, carrying durations and phase names only — never window titles,
   OCR text or tool arguments.
4. OCR scopes to a target rect in `click_text` and `wait_for(what="text")`,
   both via a new optional `target` argument that **defaults to today's
   behaviour**. `click_text` deliberately does not default to the active
   window.
5. `--dpi 300` stays. It costs 40% of the recovered text to remove.
6. `WEB_RENDER_SETTLE`'s unconditional sleep becomes a bounded poll with the
   same 2.0 s ceiling and the retry path intact, and the geometry is re-read
   after the wait.

## Steps

**1. `tools.py`: `grim -t ppm` at both capture sites.**
`_ocr_region` (`tools.py:1828`) and `_ocr_words` (`tools.py:1922`). Both are
`subprocess.run(["grim", "-g", geometry, "-"], ...)`; insert `-t`, `ppm`. There
are exactly two, and `grep -n '"grim"' src/omarchy_voice/tools.py` must show no
third.
→ verify by: tests 1 and 2.

**Measured after landing**, interleaved 7 runs each so drift hits both equally,
on one real `read_screen` of a text-dense screen: median **5.09 s → 4.40 s**, a
0.69 s saving. Less than the 0.91 s the standalone `grim` benchmark predicted;
the gap is unexplained and recorded rather than rounded away. It is ~14% of the
call, and the rest is tesseract, which steps 3 and 5 go after.

**2. `tools.py`: extract `_target_geometry`.**
`_read_screen_text` (`tools.py:2084-2123`) already resolves `"screen"` /
`"activewindow"` / an address to a geometry string, including the
visible-workspace guard. `click_text` (`tools.py:2016-2022`) and the text
branch of `wait_for` (`tools.py:2937-2943`) each hand-roll the monitor half of
the same thing.

Pull it out as `_target_geometry(target) -> tuple[str | None, str | None]`
returning `(geometry, error)`, and have all three call it. This is a
refactor-first step: steps 3 and 4 are one argument each once it exists, and
three copies of the geometry logic is how the two callers drifted apart in the
first place.
→ verify by: the existing `read_screen` tests pass untouched — they already
cover every branch of the resolution being moved.

**3. `tools.py`: optional `target` on `click_text` and `wait_for`.**
Add `target: str = "screen"` to both schemas and handlers, passed to
`_target_geometry`. `"screen"` is the current behaviour, so an un-migrated
caller is unaffected.

Note in the schema description *when* to pass it — "pass the window's address
when you know which window the text is in; it is faster and cannot match text
in another window". The benefit depends entirely on the model actually using
it, which is why the wording matters and why the trace has to check it.
→ verify by: test 3.

**Added during implementation:** `describe()` names the target too, for both
tools. The plan did not list it, and it has to happen: the transcript is the
only record of where a click landed, the policy gate matches that line, and
"click 'Delete'" reads very differently depending on which window it went to.
Omitted for the default monitor, so existing transcripts are unchanged, and
omitted for `wait_for` when `what` is not `"text"`, where the target is unused.

**4. `capabilities.py`: nothing.** The manifest documents tools from
`TOOL_SCHEMAS`, so step 3's descriptions carry themselves. Listed so the
absence is a decision, not an oversight.

**5. `tools.py`: replace the `WEB_RENDER_SETTLE` sleep.**
`_read_web_window` (`tools.py:2701-2708`). Replace `time.sleep(settle)` with a
bounded poll: read, and stop when the text stabilises between two reads or
passes the length the retry path already treats as "enough" (200 chars,
`tools.py:2590-2594`), giving up at `settle`. Keep the retry.

Two constraints from the spec, both from bugs the current code documents:

- A mapped window can still be blank (`tools.py:2704-2706`), so existence is
  not the predicate — only pixels are.
- Re-read the window's geometry after the wait. The current code computes
  `geometry` once and OCRs the old rect if the window was still being placed.

Give the poll a floor so a page that paints one header in 50 ms is not read as
finished.
→ verify by: tests 4 and 5.

**Deviation found while implementing.** A wall-clock deadline alone was wrong
twice over. It busy-spun in every test that stubs `time.sleep` — the suite went
from 14 s to 26 s — and more importantly the poll interval was fiction: an OCR
read of a browser window costs 1–4 s on this machine, so the first read alone
spends a 2 s budget and nothing is ever "polled" at 0.25 s. The loop is now
bounded by attempts *and* the clock. In production the deadline stops it after
one read, which is the honest description of what it does: wait a short floor,
read once, and only read again if there is budget left.

**6. `tools/bench_local.py` and a new `src/omarchy_voice/trace.py`: the trace.**
A `Trace` object collecting `(phase, name, monotonic)` events, with:

- `Executor` emitting phases around lock acquisition, each subprocess (by
  `argv[0]` only), capture and OCR.
- The brain emitting a phase per model turn boundary.
- A reducer computing p50/p95 task completion, **dependent model
  continuations** and wrong-target rate.

"Dependent continuation" counts a model invocation that happened *because* a
tool result was awaited. Several tool calls in one model response are **one**
continuation, not several. Getting this wrong makes every later
composite-tool argument unfalsifiable, which is the whole reason the metric
exists.
→ verify by: test 6.

**Deviation: `tools/bench_local.py` is not wired up, and the flag is.** The
bench calls the real Claude Code CLI and the real ElevenLabs API, so I cannot
run it here without spending someone's quota — wiring it would mean shipping
unverified code on the strength of it looking right. The `session.log` path
covers the need it was there for (whole-task traces from real use, not only
from scripted tasks), is tested, and was checked against a live task:

    TIMING  3.36s continuations=0 capture=0.07s lock=0.00s model-turn=3.36s
            ocr=3.19s tool=3.36s

which is the first whole-task number this project has had, and says plainly
that capture is now 2% of a read and OCR is 95%. Left open for whoever can run
the bench.

**7. `config.py` + `trace.py`: the `session.log` flag.**
A `[hands]` key beside `allow_shell` (`config.py:356`), `desktop_control`
(`:361`) and `allow_notifications` (`:377`), defaulting `False`. When on,
`feedback.log` receives one line per completed task: phase names and
durations.

The redaction is the point, not a detail. The emitter takes durations and
phase names and **has no parameter that could carry a title, an OCR string or
a tool argument** — a filter that strips them is a filter that can be wrong.
→ verify by: test 7.

**8. `README.md` and `share/config.example.toml`:** document the flag under the
same "off by default" list that #19 established, saying what it records and
what it does not.
→ verify by: read it.

**9. Drive-by, in scope because it is in these functions.** Two error messages
still tell the model to "switch to it first with `hl.dsp.focus`"
(`tools.py:2118`, `tools.py:2869`) — advice #22 made invalid, since
`hypr_dispatch` no longer accepts Lua. Both are in code steps 2 and 3 touch.
Reword to the structured form.
→ verify by: `grep -n 'hl\.dsp\.focus' src/omarchy_voice/tools.py` returns
nothing.

## Tests

Plain `unittest`, `sys.path.insert` header, `Executor._shell` as the seam where
it applies. The two capture helpers call `subprocess.run` directly, so those
tests patch `subprocess.run` in the `tools` namespace.

1. **Both captures ask for ppm.** Patch `subprocess.run`; assert `-t ppm` in
   the argv of the `grim` call, for `_ocr_region` and `_ocr_words`.
2. ~~**PPM does not change what is read.** A checked-in fixture image, encoded
   both ways, produces identical tesseract text.~~ **Deviation:** replaced. The
   only way the container could reach tesseract's output is PNG's `pHYs`
   resolution chunk, which PPM has no equivalent for. Checked: grim's PNG has
   no `pHYs` (IHDR, IDAT..., IEND and nothing else), and both call sites pass
   `--dpi` explicitly regardless. Verified once on a real frame converted
   losslessly to both formats — OCR byte-identical, 6029 characters each — but
   that needs a live desktop. So the test pins the *mechanism*: both helpers
   pass `--dpi`, and if that ever stops being true the format starts to matter
   and the test fails. A checked-in fixture would also have meant committing a
   screenshot of this desktop.
3. **`target` scopes the capture, and the default does not.** `click_text` with
   a window address captures that window's rect; with no target it captures the
   focused monitor, byte-identical argv to today.
4. **Nothing sleeps unconditionally.** A window whose first read returns plenty
   of text completes in well under the 2.0 s ceiling — asserted on a fake
   clock, not by timing the test.
5. **A blank page still gets its full wait and its retry.** A window that reads
   empty throughout consumes the ceiling and still retries once, as today.
   Paired with test 4 so "faster" cannot be bought by giving up early.
6. **One model response with three tool calls is one dependent continuation.**
   A synthetic phase sequence through the reducer. This is the test that keeps
   the composite-tool argument falsifiable.
7. **The flag is off by default, and on it leaks nothing.** With the flag on, a
   task that reads the screen and clicks text produces log lines containing
   durations and phase names, and containing none of: the OCR text, the window
   title, the clicked string. Asserted by putting a distinctive sentinel in
   each and searching the log for it.

nix flake check                                        # green
nix develop -c python3 -m omarchy_voice verify-gate    # exit 0

## Rollback

One branch, `perf/26-capture`. Nothing outside the repo changes and no state
migrates, so `git revert` the merge and restart the daemon.

Each step is independently revertable and they are ordered so that reverting a
later one does not disturb an earlier one — step 1 is two flags, step 3 adds an
argument with today's default, step 5 is confined to one function. The trace
(steps 6–7) is additive and off by default, so reverting it cannot change what
the assistant does.

The one thing to watch after a partial revert: step 2 extracts
`_target_geometry` and three callers depend on it, so it is the step to keep if
any of 3–5 come out.
