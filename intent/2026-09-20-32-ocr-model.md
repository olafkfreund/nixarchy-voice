# Intent: every OCR knob was chosen deliberately except the one that matters most

## Problem

OCR is the expensive thing this assistant does. #23 measured it as the
dominant cost and made it the reason the whole desktop-loop chain exists.
Every parameter of the tesseract call has been argued over and written down:

- `--psm 3` carries a comment explaining why `psm 6` was rejected — it could
  not see the "Files changed" tab on a GitHub pull request at all
  (`tools.py:226-232`);
- `--dpi 300` is #26's approved decision 5, kept because removing it costs 40%
  of the recovered text;
- `--oem 1`, `preserve_interword_spaces=1` and `-l $OMARCHY_OCR_LANGS` are all
  explicit in `tools.py:1981-1984`.

**The recognition model is not.** `nix/package.nix:9,67` takes plain
`tesseract` from nixpkgs and puts it on the wrapper's PATH. Nothing in this
repository mentions `tessdata` or `traineddata`; `grep -ri` returns nothing.
What we inherit on this host is the **`best` family** — `eng.traineddata` is
23,466,654 bytes, against roughly 4 MB for `fast` and 15 MB for the standard
set — and `best` is the slowest of the three by design.

So the single largest lever on the slowest step in the loop is the one thing
nobody chose. That is the problem, and it is not the same as saying the current
choice is wrong.

Measured on this host, same PPM capture of one 2560x1440 monitor, the exact
arguments `_ocr_region` uses, mean of three runs:

| model | mean | words |
|---|---|---|
| `best` (23 MB, what we ship) | **2330 ms** | 481 |
| `fast` (4.1 MB) | **1899 ms** | 475 |

18% faster, and **not** a free win: unique-token overlap between the two
outputs is only 67%, each recovering tokens the other misses. Worth stating
plainly, because the file-size gap invites the assumption that it is a large
speedup and it is not.

The more uncomfortable finding is what both outputs contain. Real tokens from
the `best` run include `wordow`, `Toaay`, `1ssues-«` and
`Xpiinsitbelpackaging`. If the most accurate model available is this noisy on
our own UI, that is evidence about how much weight `click_text` and
`read_screen` can carry — and an argument against investing further in making
pixel OCR faster rather than needing it less.

## Proposed outcome

- The recognition model is a decision this repository made, with the reasoning
  next to it, rather than whatever nixpkgs defaulted to.
- Someone benchmarking OCR here knows which model they are measuring without
  stat-ing a store path.
- The speed-against-accuracy trade is recorded from measurement rather than
  re-derived by the next person, whichever way it is settled.
- If the model does change, it changes because task outcomes moved, not because
  a stopwatch on one image did.

## Affected users and systems

- Everyone using `read_screen`, `click_text` and `wait_for(text)` — the whole
  OCR surface, on every backend.
- `nix/package.nix` (the `tesseract` input and `runtimeInputs`), and whatever
  documents the choice.
- Anyone setting `OMARCHY_OCR_LANGS` for a non-English desktop: a model family
  is chosen per language pack, so this must not quietly break non-`eng` users.
- Closure size. `best` to `fast` is roughly 19 MB per language.

## Constraints

- **Must not switch on the strength of a microbenchmark.** #23 is explicit that
  changes are argued against p50/p95 task completion, dependent model
  continuations and wrong-target rate. An 18% figure from one screen is exactly
  the kind of number #23 refused to let drive a decision, and this intent must
  not smuggle it back in.
- **Must not break `OMARCHY_OCR_LANGS`.** Whatever is pinned has to cover the
  languages a user can already ask for, or say plainly which it does not.
- Must not undo #26 decision 5 (`--dpi 300`) or the `psm 3` reasoning by
  accident — a model change interacts with both, and neither was free to
  establish.
- The result must be checkable. A pinned model that nothing verifies is the
  same accident with a different owner.

## Open questions

1. **Pin what we already have, or change family?** Pinning `best` explicitly
   and writing down why is a complete answer to this issue and costs nothing.
   Changing to `fast` is a behaviour change on 67% token overlap and should
   need more evidence than exists today.
2. **What evidence would justify a change?** My view is wrong-target rate from
   #26's trace, measured per model over real tasks — not latency on a fixed
   image. That is a larger piece of work than pinning, and may be a separate
   issue.
3. **Does this need to be per-language?** `fast` and `best` exist for most
   packs but not uniformly, and `OMARCHY_OCR_LANGS` lets a user ask for any of
   them.
4. **Is `tessdata` the right seam?** nixpkgs exposes `tesseract.override` with
   a `tessdata` argument, so the family is selectable without packaging
   anything here. Whether the data sets we want are already in nixpkgs, or
   would have to be fetched, is unestablished.
5. **Given the noise in both models, is this worth doing at all beyond the
   documentation?** A pin plus a written trade is cheap and clearly useful. Any
   further OCR tuning may be effort better spent on needing OCR less, which is
   #31's territory.
