# Intent: one command proves the policy gate still holds

## Problem

#7's guarantee — every Claude Code tool call passes our policy — rests on
three behaviours of the installed `claude` CLI, measured on 2.1.274:

1. a `PreToolUse` hook `deny` blocks a call the CLI would have auto-approved;
2. an explicit hook `allow` means `can_use_tool` is never called;
3. an exception raised in a hook lets the call **run**, which is why the hook
   never raises.

None of these is ours. A Claude Code upgrade can change any of them, silently,
and the gate would then fail in exactly the way #7 fixed — open, with every
unit test still green.

The unit tests cannot see it: they call the hook directly, so they prove the
rules are right when called and nothing about whether the CLI calls them. The
CI from #12 cannot run it either: it needs a logged-in CLI and spends plan
allowance.

What does see it is the live table from #11:

| Case | Expected |
| --- | --- |
| A — `Read` inside cwd, deny rule on its name | refused, nothing leaked |
| B — `Read` outside cwd, no rule | runs once, no `ALARM` |
| C — `EnterWorktree` under `--dry-run` | narrated, no worktree created |
| D — the policy forced to raise | refused, `ERROR` logged |

Today re-running that means rebuilding a throwaway script from a PR
description. So in practice it will not be re-run, and the next upgrade that
changes hook behaviour will go unnoticed.

## Proposed outcome

After any Claude Code upgrade, one command runs cases A–D against the
installed CLI and ends with a plain pass or fail — naming the case that failed
and what was observed instead. A failure means "do not trust the gate on this
CLI version until this is fixed".

Observable: on today's CLI the command passes all four. Breaking the gate on
purpose — say, removing the hook's catch-all — makes it fail on the case that
covers it.

## Affected users and systems

- Whoever upgrades Claude Code on a machine running omarchy-voice.
- A new file under `tools/`, beside `bench_local.py` and `bench_realtime.py`,
  which already hold the "run by hand against the real thing" checks.
- Possibly a line in README where the claude-code backend is described.
- Nothing in the runtime: the tool drives `ClaudeBrain` but ships no change
  to it.

## Constraints

- **Leaves nothing behind.** Every file and git repository it needs lives in
  a temporary directory that is removed afterwards, pass or fail — including
  any worktree a regressed case C manages to create.
- **Nothing dangerous, even when failing.** The spike showed the probes are
  benign when the gate is open: reading a grocery list, creating a worktree in
  a throwaway repo. It stays that way.
- **Neutral names.** A first attempt named files `canary7` and the model
  recognised a test and refused before calling any tool, which proved nothing.
  The probes must read like ordinary requests.
- **Honest about cost.** Each case is a real model turn on the plan's
  allowance; the tool says so before it spends anything.
- **Not in CI**, and says why.

## Open questions

1. **A `tools/` script, or an `omarchy-voice doctor --gate` flag?** A flag is
   discoverable where people already look, but it would make `doctor` spend
   plan allowance and take a minute, which `doctor` never has. I would keep it
   a `tools/` script and have `doctor` print the command next to the CLI
   version it already reports.

2. **Should it remember the last CLI version that passed,** and have `doctor`
   warn when the installed version differs? Useful — it turns "remember to
   re-run" into something the machine notices — but it is state, and more
   than the issue asked for. I would leave it out and revisit if the manual
   step keeps being forgotten.

3. **What about a model-level flake?** Case A depends on the model choosing
   the `Read` tool when asked; it could phrase-dodge and prove nothing. The
   spec needs to tell "gate failed" apart from "model did not make the call"
   — the second is an inconclusive result, not a pass.
